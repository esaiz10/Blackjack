============================================================
1. Executive Summary
============================================================

This capstone project is a cross-platform casino app built with Expo and React Native.
The poker portion implements a playable Texas Hold'em experience with one human player
against four AI players, plus persistent data tracking through Firebase.

The poker module includes:
- Full hand lifecycle: preflop, flop, turn, river, showdown
- Betting actions: check, call, raise, fold
- Blind posting and turn-order logic
- AI decision-making based on hand strength and pot odds
- Hand evaluation and deterministic tie-breaking
- Firestore persistence for outcomes, sessions, and per-hand records

The app runs on web, iOS, and Android from a single codebase.

5. Poker Module Functional Documentation
============================================================

5.1 Table Configuration
- Players: 5 seats total (1 human + 4 AI)
- Starting stack: 1000 chips per seat
- Blinds: Small Blind 10, Big Blind 20
- Streets: preflop -> flop -> turn -> river -> showdown

5.2 Gameplay Features
- User actions: check, call, raise, fold
- Human raise sizing via draggable slider (5-chip increments)
- AI auto-actions during its turn
- Pot and street bet tracking
- Hand conclusion by fold-out or showdown
- Hand result and bankroll impact persisted to Firestore

5.3 Turn Order and Betting Flow
- Preflop order starts from UTG and proceeds through blind seats
- Postflop order starts from first active seat
- On raise, action re-opens to remaining active players
- Betting rounds close when all active players are matched/checking or folded

5.4 Hand Evaluation and Winner Selection
- Best 5-card hand is selected from 5-7 cards
- Ranking supported from High Card to Royal Flush
- Ties resolved by deterministic tiebreaker arrays
- Winner or tie result drives payout and persistence events

6. Poker AI Design
============================================================

File: components/pokerAI.js

AI strengths:
- Uses explicit strength tiers:
  weak, weak_medium, medium, medium_strong, strong, very_strong
- Applies different logic preflop vs postflop
- Uses pot odds (call ratio) to gate calls and folds
- Uses positional looseness in late position preflop
- Includes controlled bluff and trap behavior

Decision outputs:
- fold, check, call, raise

Training/tuning:
- scripts/pokerSim.js performs self-play parameter sweeps
- Tuned parameters are written back into pokerAI.js
- The checked-in file indicates tuned values stamped on 2026-03-04

7. Data Model and Persistence
============================================================

7.1 Authentication
- Firebase Auth with email/password
- User session persistence:
  - Web: browserLocalPersistence
  - Native: AsyncStorage-backed persistence

7.2 Firestore Collections Used by Poker

A) stats/{userId}
Aggregated counters, including poker:
- poker.wins
- poker.losses
- poker.ties

B) games
One summary row per completed poker hand result:
- userId
- gameType = "poker"
- result = win/loss/tie
- playerScore (used as stack snapshot)
- playedAt

C) pokerGames
One document per poker session:
- userId
- startedAt
- endedAt
- handsPlayed
- wins, losses, ties
- startStack
- finalStack
- netChips

D) pokerGames/{gameId}/hands
One document per hand in a poker session:
- hand metadata (number/time)
- result
- pot and stack values
- cards and board state
- street action context
- end reason (showdown/fold)

9. Security and Configuration
============================================================

Environment variables:
- EXPO_PUBLIC_FIREBASE_API_KEY
- EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN
- EXPO_PUBLIC_FIREBASE_PROJECT_ID
- EXPO_PUBLIC_FIREBASE_STORAGE_BUCKET
- EXPO_PUBLIC_FIREBASE_MESSAGING_SENDER_ID
- EXPO_PUBLIC_FIREBASE_APP_ID
- EXPO_PUBLIC_FIREBASE_MEASUREMENT_ID

Recommended Firestore rules:
- Allow reads/writes only for authenticated users
- Restrict each user's stats/sessions to matching auth UID
- Validate expected field schema and data types

Known security limitation:
- Results are currently client-authored and written directly from app code
- A server-authoritative validation layer is not implemented yet
